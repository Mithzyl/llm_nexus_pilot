## 目标

- 要实现的结果：Agent 能发现并连续调用工具、根据失败修正操作、提交有依据的结果；需要新逻辑时能在获准环境创建、验证并使用任务工具。
- 要实现的结果：模型只能调用注册工具；工具输入由明确 Schema 校验；文件、命令和 Git 操作只能发生在绑定的隔离 Workspace 内。
- 要实现的结果：超时、取消、输出过大、路径越界、权限拒绝、进程异常和结果保存失败都有稳定错误和审计事实。
- 本文统一规划模型工具循环、工具发现、代码组合、生成工具、批准交互和外部工具接入；按下面工作项分别验收，不把尚未开始的能力标为可用。通用队列/Worker机制引用阶段10，不重复设计；第一项本地交付不开放网络、外部写入、运行时安装或自动全平台发布。
- 明确不处理：把任意 Shell 字符串、宿主机目录、环境变量或 Docker Socket 直接暴露给模型。

### 首批实现与调用方式（2026-10-19）

原修改和统一规划已提交为 00fe580；新工作位于 codex/general-agent-tool-loop。首批开放已有授权只读文件工具；后续增加仅限当前 Task 的笔记保存/读取（下节），不是外部文件写入。不接 Shell/Python、联网或自主创建工具。

现有 POST /api/v1/runs/{run_id}/agent-workflows 显式接受：

- workflow_name = general_agent
- workflow_version = 1.0.0
- execution_profile = general_tools_v1
- review_policy = always / on_verification_failure / never
- idempotency_key、stream 和实际已登记模型的 role_bindings 沿用原接口。

必须提供 controller 模型绑定，非 never 时还需 reviewer 绑定。Controller 绑定在此表示主 Agent 的模型，不表示已调用独立规划节点。旧 model_only 版本和默认请求不变；附件自动启用旧工具配置的逻辑不覆盖新定义。运行从持久请求恢复固定配置，不接受途中改审核策略。

实际流程：主 Agent 普通正文/原生工具循环 → 后端候选记录 → 按策略审核或修正 → 保存正文及限制 → 完成记录。最终保存没有额外模型调用，也不要求模型包装复杂 JSON。Reviewer 当前返回小批 decisions：每项只有 unit_id、verdict（supported、revise、unconfirmed）、feedback 和短 source_aliases；不要求 Provider JSON 模式。每次最多6个单元是请求大小控制，不是工作流调用总数限制；所有批次共用同一 Reviewer 时间期限。每个批次最多一次格式/引用修正，保留已校验决定，仅重发不合格单元。内容修正回到原 Agent，保留工具消息、加载版本、无进展检测及原截止时间；修订后按原策略重新审核。

- always：每版候选的全部段落/条目/代码单元均审核。on_verification_failure：未知来源编号、读取后完全缺少引用、部分段落无引用等问题触发审核。部分段落缺引用只要求 Reviewer 判断是否需要依据，不把一般建议强制补成文件结论；未知编号等真实引用错误不能被 Reviewer 批准。never：不调用 Reviewer，但引用错误仍须修正。权限撤销、损坏对象和快照不符直接失败，不能由审核批准。
- 后端为成功读取结果分配 [S1] 等运行内编号，保存真实调用、文件、原件/解析哈希及块范围。新候选正文版本为 general_candidate.v2，历史 general_candidate.v1 仍可读但不补造分段；审核输出类型仍为 general_review。Reviewer 获得被引用原文、候选段落、工具返回范围和解析限制，并可补读；补读原文随反馈返回主 Agent。每次调用前核查共享来源权限，交付前重新核对引用。
- supported 是审核模型的判断，不是确定性真值；unconfirmed 可以带明确的未确认说明交付。非法格式、引用持续无效、重复无进展及取消不能冒充成功。v2 已加入后端段落/条目位置和短引用关联；代码示例不当引用，未引用段落不自动继承附近来源。unit_id 仅在当前候选节点内有效，偏移按 Unicode 码点而非字节或 JS UTF-16 计数；读取时校验原文位置、不重叠和内容没有遗漏。
- v2 同时按 file_id/原件哈希/解析哈希/parser_version 保存去重的实际返回块、总块数、未返回数量及解析警告。搜索范围不计为返回范围，工具返回不等于所有内容进入模型当前输入，更不等于已理解。未被任何工具返回的文件不在该候选集合内，不能据此宣称完成所有附件。逐单元审核及条件触发已有代码、确定性测试和真实 Strata 成功样本；实际请求的原生文件工具及后端单独传入的原文集合已有输入清单（见阶段2）。执行中可查询任务已返回/未返回范围，见下方读取进度工具；任务级实际模型输入汇总和执行检查点仍待补齐。任务笔记不能替代这些范围事实。
- general_review.v2 由后端关联 candidate_node_id、保存全部有效单元决定及真实短来源映射，并计算总体处理方式：有 revise 则修正，否则有 unconfirmed 则带限制交付，全部 supported 才将总体决定标为 supported。缺少/重复/其他单元编号、未知来源及不一致总体结论拒绝。历史 v1 整篇审核仍可读，不伪造逐项决定。模型说明内容是否支持，程序校验来源真实性，两者不能互相替代。
- Reviewer 实际输入只列出本批单元编号/类型/正文/短来源，同时保留完整候选正文以理解上下文；不重复提供其他批次编号或平台 citation_status，避免与模型决定混淆。运行内正常模型请求序号连续，批次修正有独立请求 key；output_repair 事件以节点+批次计数，不把同一节点的多个修正合为一次。真实样本仍需每批一次格式修正，开销和失败记录见验收文档。
- 原 claim-sources 查询支持新单元，按 candidate_node_id/unit_id 查实际持久引用，再重查权限/快照；不接受客户端提供任意引用。旧查询不变。Web 仅增加类型/数据适配，最新候选与旧审核不得串配，复用既有组件/标签；没有改样式、布局或默认运行定义。
- 内容修正用 workflow_round 和 refinement 事件统计；格式修正用 output_repair 事件及实际 Attempt 统计。工具调用不是业务轮次。新流程不继承旧“两轮”限制，max_model_calls=0 仍表示无调用计数上限；现有节点数、运行/角色时间、窗口、工具批量及正文保存限制继续适用。旧 max_workflow_rounds 字段只作用于旧流程。
- 复用 Run、Task、Workflow、Node、Attempt、ModelToolCall 和事件表。正文、来源映射使用已有 ConversationBodySession、body_ref_json 和 MinIO 路径规则；无新增 SQL 表、迁移、桶或旧对象改写。新结果需由支持新类型的 API 代码读取，不能交给旧 API 解析。
- 不创建虚构的 Agent Run/Handoff/Evaluation。当前主 Agent 可按需调用已配置的 Planner/Researcher，创建实际子任务、Agent Run与v3 Handoff，详见下节；不递归委派。SSE 观察断开不取消执行；显式停止和迟到用量沿用既有规则。终态结果可查询，重复请求不会重新调用模型；没有跨进程续跑。

实现入口为 features/agent_runtime/services/general_agent_orchestrator.py。为控制修改范围，仅继承旧协调器的持久化/记账辅助方法，不调用其固定 execute 流程。快速回复独立循环本批未合并，公共 Gateway、文件执行及历史投影继续共用。

### 用户结果与当前证据

同一个 Agent 能根据用户目标选择检索、连续阅读、计算、写文件、验证或委派，不为每种任务单独建立一条必经节点链。先实现已有授权只读工具上的连续任务，再接通用执行器；不以本规划自动开放命令、网络或写操作。

默认兼容入口仍有两种文件工具循环，旧 Agent 外层依次规划、分派、交接、验证、审核和汇总，并要求复杂节点 JSON；首批新方式仅显式启用。2026-10-18 Strata 完整 PDF 联调在旧 Worker 首次输出及一次修正后失败；7 次调用的原始 SSE 独立拼接、适配器与 MinIO 正文一致，最后修正是正文中间 JSON 非法而非保存丢字。说明必须减少业务内容与平台记录格式的耦合；不能推断长上下文是唯一原因或所有模型均不可靠。完整证据见[联调记录](strata-long-files-verification-20261018.md#完整-agent-工作流逐调用-sse-与保存结果对照)。

### 执行流程与职责

1. 后端固定用户目标、Run、允许来源、工具版本、模型配置、审核策略及明确资源限制；创建可持久恢复的执行记录。不默认要求先生成完整任务图。
2. 模型读取目标、必要历史和工具说明，输出普通文本、完整工具调用，或两者组合。完整参数到达并通过校验前不执行工具。
3. 后端保存调用意图，检查归属、权限、参数、版本与副作用；执行工具并保存原始结果，再用对应调用 ID 返回结果。平台生成身份、状态、引用、耗时和用量，不让模型重写执行档案。
4. 同一个 Agent 根据实际结果继续搜索、阅读、计算、修改计划或请求协助。普通步骤不切换角色，不强制 Handoff。工具失败是可识别的结果，不应变成空成功；未知副作用和权限拒绝不能换工具绕过。
5. 无工具调用的普通文本是候选答案，不要求包装复杂业务 JSON。后端根据已固定审核策略决定直接交付、进入审核、要求局部修正或等待必要信息；不能从模型口头“审核通过”设置终态。
6. 必须审核时调用 Reviewer 能力；审核意见返回原 Agent 或 Controller 形成内容修正，再由同一循环执行。是否委派、如何拆分由任务需要决定，授权、审核条件和已选策略不可由模型更改。
7. 保存实际最终正文、产物、来源和终态。取消后不继续汇总；观察断开不等于取消，跨进程恢复依赖阶段10。用户输入/批准的等待与恢复接口尚未实现时，不宣称可恢复暂停，返回明确的等待原因。

快速回复与 Agent 最终共用工具执行、历史投影、取消和记账机制，但保留两个产品入口及历史 API。快速回复不因上传附件偷偷升级为多 Agent；通用 Agent 可按任务规划/委派并执行用户选择的审核策略。合并实现不意味着改变现有默认权限或把两种模式合为一个按钮。

### 工具集、发现和扩展

工具按能力组织：材料目录/搜索/读取、任务笔记和计划、受控计算/文件操作、结果验证、按需委派与审核。这里是目标分类，不是新增可调用工具名。首批复用现有五个附件工具和目录加载规则，后续工具参数、版本及作用域仍由注册定义生成；不同时注入所有工具 Schema。

### 模型正文与后端结构化结果

工具调用参数和控制执行的小型决定继续严格校验；普通分析与最终答案允许自然语言。`response_format`/原生 Schema 只用于确需结构化且能力验证通过的操作，不作为通用 Agent 最终回复的全局要求。

证据任务中，后端从真实工具结果生成稳定的短来源编号；模型用正文及短引用表达依据，后端解析并展开为文件/原件哈希/解析快照、调用和块范围。编号作用域固定在 Run 及明确授权的委派链内，恢复不重新编号、跨 Run 不凭编号复用，访问时重新鉴权。编号映射及读取事实不能由模型生成或覆盖。

需要逐结论审核时，后端将正文段落/条目作为候选结论单元，保留原始正文和位置，不声称完成语义原子拆分。无引用、非法引用、混合断言分别标注，不用额外模型把整份正文重写为复杂 JSON，也不自动猜来源。正式 JSON 由后端类型构建；知识解释、代码产物等无文件来源的任务不被强行套入文件 claims 结构。

Reviewer 只提交结论标识、审核决定、必要理由和短来源等小型输出；可按批次处理，坏决定只修正对应部分。输出方式须在实施时用已登记模型验证并固定，不能将“支持 tool use”当作“小型审核格式必定正确”。结构无法识别不算通过。引用有效和结论获原文支持分开记录；内容修正不覆盖旧结论或旧审核版本。最终汇总输出自然语言，由后端保存，不再生成完整节点业务 JSON。

### 一份定义用于模型和执行器

当前 `RegisteredTool` 已实现内置工具名称/版本、用途、关键词、输入输出类型、所需能力及默认加载标志；`packages/models.ToolDefinition` 是模型请求结构。执行仍由受信服务中的固定实现分派，不支持模型注册代码。下文完整目标还包含示例、执行实现引用、运行环境/依赖、错误/重试规则及结果读取方式，随动态工具和执行环境补齐。平台从同一输入定义生成 Provider Schema，避免模型参数与实际执行参数漂移。

- 执行实现分为内置函数、隔离脚本、组合程序和后续 MCP 适配器。模型调用方式一致；不必为每种工具增加一种 Agent。
- 内置工具可由 Pydantic 类型生成 Schema；生成工具只接受受支持的声明式 JSON Schema，经独立校验器验证。不在 API 进程导入或执行模型生成的 Python 类型/注册代码。
- 工具的说明、示例、只读标记及生成者自报的权限都是待核对资料，不授予访问权。注册后的版本固定代码哈希、Schema、依赖工具版本和镜像 ID。
- 模型只提交工具名、调用 ID 和业务参数。owner、任务目录、允许的文件与网络目标、凭据引用和资源上限来自服务端关系和策略。

### 可搜索目录

2026-10-09 已实现 `search_tools` 与 `describe_tools`，目录目前仅包含内置只读工具，不含个人/项目/外部工具。首轮加载 `list_run_files`、`read_file_content` 和两个目录工具；文件结构、表格、正文搜索的 Schema 按需加载，避免每轮发送所有定义。

- `search_tools(query, offset, limit)`：按名称、用途和中英文关键词作不区分大小写的字面匹配，先过滤服务端能力许可，再稳定排序分页。关键词为空列出可见工具，无匹配返回空列表。首版不提供向量检索或输入/输出类型筛选；不访问外部目录。
- `describe_tools(name, version)`：读取精确版本的输入/输出 Schema 和用途，记录成功后才将该版本加入当前 Worker 的下一轮模型请求。同一响应批次中抢先调用尚未加载的工具返回 `tool_not_loaded`；加载变化后可以重新提出该调用，不误判为无进展。未知、不可见或错误版本统一返回 `tool_unavailable`，不静默升级。
- 同一个工具名称仅允许一个活动版本，重复名称在登记时拒绝。加载状态不在 Worker 间共享；每次生成请求及执行时重新检查许可和版本。搜索/说明结果再次进入模型历史前也检查版本是否仍可用。
- 每轮 Attempt 的私有请求 metadata 保存 `loaded_tool_versions` JSON 字符串，兼容现有字符串型 metadata；目录调用与读取调用均写入 `llm_tool_calls`，使用既有预算和进度事件。Web 显示“查找可用工具”“查看工具说明”，不向前端暴露 Schema、内部实现引用或凭据。
- `available` 仅说明当前内置实现可调用，不保证某个文件存在、归属正确或已解析；实际文件授权与状态仍在执行前检查。动态工具的缺依赖、个人/项目可见性和外部连接状态需在对应来源实现时补齐，不返回虚构的能力。

## Agent 持续调用与失败处理

本节说明已有 `tool_enabled_v1` 内层循环及其恢复要求；新默认目标由文首“通用 Agent 工具循环目标设计”维护。当前附件循环、逐结论引用及 Reviewer 原文核对已有本地实现；跨进程恢复和 Agent 通用代码执行尚未实现，不能把下面恢复要求当成已上线能力。

`tool_enabled_v1` 复用现有 Controller/Worker/Handoff/Reviewer；先支持一个 Worker 内的工具循环，再扩展多 Worker。每轮流程如下：

1. 从已提交状态恢复任务目标、消息、来源、已加载工具版本和执行许可，经现有 Context Builder 组装模型请求。
2. 模型返回完整工具调用或最终节点结果。流式参数未完整到达前不执行；中间轮不强制符合最终节点 JSON。
3. 保存本轮调用意图，校验 Schema、绑定资源和权限，持久提交后领取执行权；同一调用不可被两个执行者同时启动。
4. 无依赖只读调用可在配置并发内执行；读写冲突、同目录写入串行。需要前一步结果的调用等待结果，不靠模型自报“并行安全”。
5. 保存工具结果、错误、产物和公开事件；按原调用 ID 回填 Tool Message。Provider 必需的私有续接信息按现有模型层策略保留，不公开隐藏推理。
6. 已有版本提交节点 JSON 后进入旧 Handoff/审核/汇总；新执行方式则允许同一 Agent 继续处理并提交自然语言候选，按固定审核策略选择后继动作，不要求所有任务进入交接链。运行代码/等待批准仍须对应能力实际接通后才可执行。

参数错误、无匹配、依赖缺失、权限拒绝、部分结果和结果未知分别返回。非法参数不得原样自动重试，但 Agent 可根据错误提出参数已修正的新调用；拒绝访问不能触发换工具绕过。外部副作用或命令是否完成不明时，先调查状态，不自动重复执行。审核意见不吞掉已有可用结果；终止时向用户说明已完成部分和不能继续的原因。

停止条件为完成目标、等待用户信息/批准、显式取消、确定不可恢复、连续无进展或达到配置的运行时间/调用/资源预算。阈值需可配置并记录实际触发原因；不新增统一低输出 token 上限。相同失败参数重复、相同结果无新行动要计入无进展检测，不以无限循环代替持续工作。

工作流状态只引用模型调用和 Tool Call 事实，不复制第二套用量/结果。上下文需压缩时保留工具版本、已执行动作、错误、产物引用和读取位置，缺少必要原文时通过授权工具重读，不能把摘要当全文。

### 节点输入输出与信息来源

| 对象 | 模型负责 | 平台负责 | 下游获得什么 |
|---|---|---|---|
| Controller 计划 | 目标拆分、任务、依赖和完成条件 | 角色/能力/预算/依赖校验，持久化身份 | 可执行任务及用户目标，不允许模型伪造工具已完成状态 |
| Worker 阶段结果 | 结论、依据引用、推测、未解决事项及其范围 | 校验结果结构与引用；记录实际读取范围和解析限制 | 业务结果、必要原文片段、可再读取的来源引用 |
| Handoff | 不要求模型另造一份平台记录 | 保存阶段结果和原引用，补齐身份、状态与真实工具记录；不可把引用压缩为摘要 | 上游任务结果及其可核对来源 |
| 确定性验证 | 不调用模型判定自然语言真假 | 检查引用存在、权限、版本、调用关联、读取/截断范围；分别报告通过/失败/未知 | 可用原文及检查事实，不输出“所有结论已验证” |
| Reviewer | 对照原文判断支持、矛盾或证据不足；必要时请求补读 | 按权限解析引用并提供原文；执行有限只读补读、保存过程 | 逐结论审核意见、来源和限制 |
| 最终汇总 | 回答用户，区分已支持、推测、矛盾和无法确认 | 保存回答及引用映射、关联版本和证据；不按工具成功自动认可内容 | 可查看来源的回答和仍存在的限制 |

Worker 输入包括用户目标、当前任务与完成条件、依赖任务结论及引用、所需原文片段、授权附件清单、解析警告和实际读取范围。无需把所有模型轮次复制给每个节点；大结果可分页读取，但不得只传摘要而失去再次读取原文的能力。先检查实际 Context 输入，避免重复注入相同原文。文件内容始终是待分析数据，不能改变系统指令、权限或工具许可。

### 模型输出与平台来源记录

以下仅展示业务内容和引用关系，省略了完整 Schema 的部分字段，不是可直接提交的请求。实际 `worker_evidence.v2` 引用还必须含 `file_id`、`source_hash`、`parsed_hash`、`parser_version`；调用 ID 为平台保存的 UUID，`result_id` 映射见上节，示例 ID 不是可调用资源。完整字段由 `schemas/worker_evidence.py` 和 `EvidenceWorkerModelOutput` 定义。

```json
{
  "summary": "报告描述了设备检查和生产操作。",
  "claims": [
    {
      "claim_key": "production-steps",
      "text": "报告描述了设备检查和生产操作两个环节。",
      "evidence_refs": [
        {
          "tool_call_id": "example-call-id",
          "result_id": "example-result-reference",
          "block_ids": ["example-block-12", "example-block-13"]
        }
      ]
    }
  ],
  "hypotheses": [],
  "unresolved_items": [
    {
      "text": "尚未确认设备型号。",
      "reason": "当前已读范围未发现型号，不能判断全文是否包含。",
      "evidence_refs": [
        {
          "tool_call_id": "example-call-id",
          "result_id": "example-result-reference",
          "block_ids": ["example-block-12", "example-block-13"]
        }
      ],
      "requires_more_reading": true
    }
  ],
  "decisions": [],
  "risks": []
}
```

- `claims` 是待核对的结论，不因字段名称或模型自报就获得“已确认”状态。无引用的知识解释或推测单独标注来源类别，不能伪装成附件事实。引用应来自本任务或显式允许的上游任务实际获得的结果；不可凭知道 ID 使用其他运行的数据。
- 平台向模型提供可选择的真实引用标识，再解析到现有文件 ID、固定原件哈希、解析产物及解析器版本、工具调用/结果和块位置。逻辑文件版本历史尚未实现，先使用已保存的固定原件/解析快照，不能把文件名当版本。
- 原文由平台从保存的结果读取，模型写出的引文不代替原文；需要展示引文时核对其与对应块一致。支持可定位的段落、页码、表格/单元格位置，不对解析器未提供的位置编造数值。
- 读取事实由平台保存：本次返回块范围、分页位置、`has_more`、截断、工具错误、解析状态及遗漏。`requires_more_reading` 只是模型建议，不能覆盖这些事实；`has_more=false` 只表示当前解析结果分页结束，不代表整个原文件均已提取。
- “该两段没有设备型号”不能自动扩大为“整个附件没有设备型号”。否定结论必须注明检索/读取范围；正文全读完仍不能排除图片、页眉、文本框等未提取内容。验证器检查范围是否真实，Reviewer 判断结论是否超出该范围；不能证明时输出无法确认。
- 每次解析引用、补读及来源下载重新检查实际用户、会话/Run、文件状态和可访问范围。删除、撤权、过期或对象缺失要返回来源不可用，不能悄悄换成新版文件，也不能将受限原文发送浏览器后再隐藏。

### 格式失败与证据不足分别处理

1. Controller、Worker、Reviewer、最终汇总共享结构错误诊断：保存字段路径、错误类型、输出版本、节点及 Attempt 关联；不在公开错误中泄露系统提示词、隐藏推理或完整文件内容。
2. 模型不拥有执行状态、身份或权限字段。针对已明确无业务作用的额外字段制定按类型的白名单处理，例如 Worker 自报 `status` 可忽略并记录警告，不能由它改变平台状态；不能全局关闭 `extra=forbid` 或默默删除未知业务字段。
3. 缺失或非法必填字段先进入局部格式修正：默认最多一次额外模型调用，计入已有调用、费用和总时限；给出原结果、原 Schema 和具体错误，禁用工具，仅修正结构，不重新执行已成功的工具。安全/权限失败和未知副作用不走此修正。修正后重新执行结构、计划业务规则及引用校验，不把“格式修正”当作豁免内容变化的理由。
4. 格式修正与重新规划、重新执行任务、Reviewer 补读是不同动作，分别记录尝试及原因。不得把缺 `title` 的修正包装成完整工作流重跑，也不得自动代填会改变任务目标、角色或权限的字段。
5. 证据不足时 Reviewer 可提出受限文件补读请求；平台执行现有只读工具并回填实际原文、保存调用，受剩余预算和有限补读轮次约束。本地已复用现有循环，具体次数及失败行为见本轮实现。无法读取时模型应提交“证据不足”；若模型不遵守最终提交要求，节点仍明确失败，不无限循环或绕过授权。
6. 失败时保留已提交工具结果和阶段结果，说明已完成工作及停止原因；必要时使用平台生成的失败说明，不能将未审核候选文本冒充已完成最终答案。审核请求重试/重规划仍只是意见，除非后续明确实现相应执行分支。

| JSON 格式 | 多余 Worker `status`、缺失任务 `title`、非法字段、修正仍失败、调用预算耗尽分别有明确结果；成功读取不重复执行，调用用量不丢失 |

| 原文一致性 | 平台提供保存的原文而非模型引文；引用块和表格范围可定位；对象缺失明确报错 |
| 结论准确性 | 固定样本包含“摘要写错而原文明示设备型号”，Reviewer 实际输入包含该原文并指出矛盾；不能仅验证第二个模型认可摘要 |
| 否定与完整性 | 分页未结束、结果截断、仅正文解析、图片内型号等样本不允许得出无范围的全文否定结论 |
| 补读与停止 | Reviewer 可根据证据缺项发起授权只读补读；不可用、取消、轮次/时间耗尽明确无法确认，不重复外部副作用 |
| 历史与界面 | 旧结果不伪造引用；新来源刷新后仍可核对；跨用户来源不下发；界面区分读取成功、引用有效、结论获支持和无法确认 |
| 真实 Provider | 经授权验证 Agent 首轮 DOCX 与续聊 PDF、最终回答保存及逐结论来源；快速回复独立文件循环回归。记录模型和环境，停止无效付费重试，离线通过不替代真实验收 |

整项验收尚未完成：本地格式修正、结论证据传递确定性测试、真实 DeepSeek/MySQL/MinIO 两段 TXT 样例及只读来源浏览器检查已执行，详见上述各自记录。最终答案逐句引用、Agent 首轮 DOCX 与续聊 PDF 的新版真实 Provider 矩阵及服务器部署验收仍未完成，不将单样例通过扩展为全部文件和模型验收。

## 代码组合与自主创建工具

### 程序调用已授权工具

Python/Shell 复用下文 `run_command` 与任务目录。先支持预装库进行计算、转换、代码检查等任务，再为隔离程序提供受控工具 SDK。程序可完成循环、条件、聚合和有界并发，避免每个确定性步骤都请求模型。大型中间数据保存在任务文件/Artifact，模型只接收所需结果及可继续读取的引用。

SDK 子调用仍通过同一执行服务，记录父调用、子调用序号、固定工具版本和任务归属；深度、总调用数、并发和耗时统一计入任务预算。组合工具的权限至少覆盖所有子调用，且每次子调用重新检查。不得给程序数据库、MinIO、Provider 凭据或通用内部服务 Key；SDK 通信采用限任务、限工具的执行绑定，不能利用 Socket 调用其他用户任务。固定解析 Socket 继续只接受解析协议，不能改成通用命令入口。

### 任务工具生命周期

拟新增 `create_tool_draft`、`validate_tool_draft`、`register_task_tool`。这是未来受控工具接口，不是已经存在的 API：

1. Agent 提交用途、输入输出 Schema、代码 Artifact、测试样本和依赖声明，形成私有草稿，不立即进入可调用目录。
2. 平台校验名称/作用域、结构、代码哈希、固定环境和依赖，再在独立临时测试目录执行；验证也视为代码执行，必须先有对应许可，不触碰真实外部写目标。
3. 测试包括平台维护的正常/错误/资源与隔离样本，以及 Agent 提交的业务样本。Agent 自测或静态扫描通过均不等于代码安全/业务完整；访问限制始终由服务端与执行环境执行。
4. 验证通过且任务政策允许时，平台注册不可变的任务版本；下一轮模型才能发现和调用。修改代码必须生成新版本并重新验证，不热替换在途调用。
5. 默认仅当前任务可用；失败草稿不自动发布。保留代码、测试结果、环境、来源和调用记录，按任务保留策略清理。
6. 保存为个人/项目工具需用户明确授权或预先批准的保存策略；全平台发布需人工审查。个人工具代码不得内嵌当前用户文件、凭据或样本正文作为通用默认值。

一次性脚本不必全部注册，只有需要重复调用或复用时才创建工具。说明与分析指引可作为后续 Skill 包装，但它不替代可执行工具定义，不赋予权限。pip 继续仅用于镜像构建；运行中缺依赖只产生依赖需求，不自动安装。

### 工作项一：统一专用解析执行方式

目标调用过程：`上传/受控 Artifact → 阶段2校验与解析适配 → 专用 Unix Socket → 宿主执行器 → 固定解析容器 → 阶段2统一结果与 Context`。这一确定性程序调用不经过模型，不要求先实现通用工具 Registry，也不伪造 Provider Tool Call 记录。

1. **先定义失败测试。** 复现现有 PDF 路径在受限 API 容器中不能工作；新增 PDF 必须通过专用执行器、执行器不可用时不回退宿主/嵌套沙箱、Office 旧请求继续可用的测试。不能把仅生成正确 Docker 参数当作真实隔离通过。
2. **扩展现有执行协议。** 已新增 `file_parse.v1`，只允许固定 MIME、文件字节和版本字段；PDF 使用固定 Poppler 程序，Office 复用原解析逻辑。保留 `office_parse.v1` 的旧 Office 请求与响应兼容，未知协议/格式明确拒绝。模型或客户端不得传入路径、镜像、命令、挂载、身份或环境变量。统一传输不要求各格式返回相同底层结构，阶段2继续转换为既有 `ParsedFileDocument`。
3. **保持提取语义。** PDF 返回页文字、页序号及解析器版本，由适配器形成现有块和遗漏信息；无文字页标记未提取，全无可用文字明确失败。Office 继续保留工作表/幻灯片位置和 `partial`，不重写历史 Context、不修改旧解析对象；新结果记录新解析版本与固定镜像 ID。不得把图像、公式推算或缺失内容写成已提取正文。
4. **改接 API 路径。** 复用 `NEXUSPILOT_FILE_RUNTIME_SOCKET`，Office 与 PDF 使用同一服务；新 PDF 路径在 macOS 和 Linux 都依赖受控 Linux 解析容器，不增加隐式本地回退。旧启动器若不再使用，实施时核对全部调用和测试后删除或限于有明确用途的历史兼容，不保留两套默认解析策略。
5. **部署目标镜像与服务。** 复用 `manage_runtime.py`、`serve_runtime.py`、`nexuspilot-file-runtime.service` 和现有 Office Compose overlay，先在 Linux AMD64 构建/检查，再部署专用用户、Socket 目录/组、镜像配置与执行器。API 仅获得解析 Socket 连接权；执行器独自持有 Docker 访问权，不共享 API/Provider/数据库环境文件。API 和解析容器均不得挂载 Docker Socket。
6. **按兼容顺序发布。** 先启动支持旧 Office 和新 PDF 协议的执行器，用合成请求确认两种协议，再更新 API 并挂载 Socket overlay。检查新 API 不再为 PDF 启动 `bwrap`。基于宿主专用组配置容器附加 GID，并从实际 API 容器验证连接，而不只检查文件存在。

执行器仍使用固定非 root 镜像、无网络、只读根文件系统、受限临时目录及 CPU/内存/进程限制；PDF 临时输入通过标准输入或固定私有临时文件交给程序，不能成为宿主路径参数。沿用当前创建/解析/清理超时与并发限制，核对客户端总超时、API 及 Nginx 超时足够容纳实际流程；超时终止本次容器并留下错误，不自动重发上传或模型调用。新增 PDF 分支的 stdout/stderr 必须有界，错误日志不含文件正文。

**发布失败与恢复：** 镜像检查、Socket 权限或合成样本失败时不更新 API；更新后失败则在无在途解析的维护窗口恢复兼容的 API/执行器镜像与配置，不删除 MySQL/MinIO 卷、旧文件或解析结果。回退到现有版本意味着 PDF 仍不可用，必须明确说明。遗留容器/Socket 先核对进程和记录，只处理本执行器创建的精确对象，不执行全局 prune。协议更新本身预计不需要业务表迁移；若实施发现必须修改持久格式，先补迁移/兼容设计，不借此重写旧对象。

## 现有模块的实现职责

本节只说明代码调用关系，交付范围和进度以文首统一工作项为准；不再把模型循环排成另一阶段的独立待办。

```text
阶段2 Model Gateway
  └── 生成标准 ToolCall，但不执行

阶段7 Tool Runtime
  ├── 注册工具
  ├── 校验参数
  ├── 判断权限
  ├── 在受控 Workspace 执行
  └── 保存 Tool Call 证据并返回 ToolExecutionResult

阶段3 Agent Runtime
  ├── 决定何时把哪些工具提供给模型
  ├── 接收 ToolCall
  ├── 调用阶段7 Tool Runtime
  ├── 把结果转换为 Tool Message
  └── 控制持续调用、取消、执行预算与最终回答
```

- 工具执行 Service 不直接读取 RabbitMQ；短循环本地验证不要求 Worker，长任务按文首后台工作项接入。
- 工具执行 Service 不自行再次请求模型；是否继续由 Agent 循环实现。这两部分均属于本计划交付，不表示循环在另一阶段等待实施。
- 执行 Service 设计为传输无关的异步 Python 接口，可由同步 API 进程或 Worker 复用。
- 可写任务必须绑定隔离任务目录；通用分析不依赖 Git。后续代码仓库修改工作项再使用独立 Git worktree，不把 Git 实现强加到所有工具的完成条件。

### Office 执行器启动与权限

执行器接受本机 Unix Socket 上一条 `office_parse.v1`（旧 Office）或 `file_parse.v1`（PDF/Office）解析请求，以及固定的 `file_capabilities.v1` 可用性探测。解析字段仅包含固定协议、允许的 MIME 和 base64 文件字节，不允许指定路径、镜像、命令、挂载或环境变量。上传先检查用户归属、原件哈希及大小，再通过 PDF/Office 适配器和共享 `file_runtime_client.py` 发送请求，校验结果来源、结构和块身份，保存解析对象；绑定会话后用于 Context 和文件工具。各 Provider 接收相同文字/表格，不直接接收 Office 字节。

本机开发先构建并通过镜像检查，再在仓库根目录的两个终端分别运行（macOS Docker Desktop 与 Linux Docker Engine 使用相同命令；目录已存在时检查归属，不覆盖或删除已有 Socket）：

```bash
# 终端 1：已有的已验收镜像，不会拉取或安装依赖。
make file-runtime-run FILE_RUNTIME_IMAGE=nexuspilot-file-runtime:unified-local
# 终端 2：确认开发数据库和备份后执行；该目标包含 api-migrate。
make api-run-with-files
```

两个目标默认使用同一 `/tmp/nexuspilot-file-runtime-<uid>/executor.sock`，可在两个命令中设置相同 `FILE_RUNTIME_SOCKET`。普通 `make api-run` 不自动启用执行器；也可在 `apps/api/.env` 显式设置实际路径后重启 API：

```dotenv
NEXUSPILOT_FILE_RUNTIME_SOCKET=/tmp/nexuspilot-file-runtime/executor.sock
```

### Linux 云服务器兼容与验收

文件解析始终运行在 Linux 镜像中；macOS 只运行 Docker 客户端和 Unix Socket 执行器，不使用 Homebrew 解析库或 macOS 沙箱执行 PDF/Office。Windows 原生执行器不在当前范围，可后续使用 Linux/WSL 主机。

在目标服务器按实际 CPU 架构构建，例如 x86_64：

```bash
python3 deployments/file-runtime/manage_runtime.py build --platform linux/amd64 --image nexuspilot-file-runtime:amd64
python3 deployments/file-runtime/manage_runtime.py check --image nexuspilot-file-runtime:amd64
python3 deployments/file-runtime/serve_runtime.py --socket /run/nexuspilot-file-runtime/executor.sock --image nexuspilot-file-runtime:amd64
```

### 本地执行器实现与运行（2026-10-09）

新增 `deployments/task-runtime/task_runtime.py` 与独立 Dockerfile；仅供受信本地执行进程或管理员调用，没有 Socket/HTTP 监听器。API 和 Web 尚不调用它，也不获得 Docker 访问权。`WorkspaceStore` 保存目录，`TaskExecutor` 执行结构化 `run_command`；相同的名称与字段供后续 Registry 接入，不另外设计面向模型的执行接口。

- 目录与权限：必须指定归当前系统用户所有的 `0700` 根目录，平台引用使用随机 UUID，记录 `user_id/run_id/task_id`，每次读写要求三者精确匹配。两项开关必须同时允许：执行器 `enabled` 与目录 `allow_execute`。这里的 scope 由受信调用方传入，**不是认证令牌**；不得直接把浏览器或模型传来的身份转交该类。真实数据库所有权检查仍待接入。
- 输入：受信调用方提供文件字节及 SHA-256，创建时检查，每次执行前重新检查完整输入集合、文件类型和哈希；容器只读挂载该目录。工作文件不以可写宿主目录挂载，而是在 32 MiB tmpfs 中运行，最多导出 128 个普通文件、每文件 8 MiB、合计 16 MiB。拒绝路径穿越、软/硬链接、特殊文件和超限输出；空文件夹也随快照保存。
- 连续性：每次 Python/Shell 是新 Linux 容器，使用上次成功保存的文件快照，不保留 Python 变量。相同任务通过跨进程文件锁串行；同一个执行根目录最多同时运行两个容器。相同调用 UUID 和参数只返回已保存的结果；改参数复用 UUID 拒绝。每个目录最多 32 次命令，保存的历史快照暂不自动删除；最多可能保留约 512 MiB 文件快照及调用记录，正式多用户启用前需补用户总配额与回收策略。
- 命令：只允许 `python` 与 `shell`，参数为相对脚本路径及脚本参数，或通过有界 stdin 提供代码；`cwd` 仅允许任务目录中的相对路径。Python 使用 `-I -B -u`；Shell 使用 stdin/脚本，不开放 `-c`。宿主始终使用 argv 数组，不执行脚本。默认执行期限 30 秒，受信调用方最多 60 秒；stdout/stderr 各保留 32 KiB，UTF-8 替换后也检查字节上限，并分别返回截断标记与退出码。这些是执行资源限制，不是模型输出 token 上限。
- 容器：本地镜像先解析为固定 ID，禁止自动拉取；非 root、只读基础文件系统、无网络、删除 Linux capabilities、禁止新权限、256 MiB 内存、1 CPU、64 进程、独立有限 `/tmp`。不传入 API `.env`、MinIO 凭据或 Docker Socket。任务镜像从已有解析镜像离线派生，保留 Office/PDF 依赖，移除 `pip`/`ensurepip`；不提供运行时安装入口。任意 Python 仍可以运行任务自身代码，不能把移除 pip 宣称为禁止所有自带 Python 模块。
- 完成与失败：只有确认仅剩固定容器保活进程后，才用固定 tar 读取 tmpfs，并在宿主校验归档。Docker Desktop 的 `docker cp` 不适合此 tmpfs 导出，不能据其空结果宣称保存成功。有效结果及调用状态落盘后再移除本次容器；非零退出可保留已验证文件，但状态仍是失败。脚本留下后台进程时拒绝本次快照；超时/取消终止整个容器、丢弃本次未完成写入，保留上一次已保存快照。
- 保存失败：冻结容器并保留具体容器名与 `executing/cleanup_pending` 状态，后续调用拒绝重跑。重建执行器对象也会发现该状态，但**没有自动恢复**；暂停容器的 tmpfs 仍会在 Docker/主机重启后丢失，因此此记录不等于持久 Artifact。完成快照以文件 fsync、目录 fsync 和状态原子替换保存。本地调用记录位于工作目录，不写入应用数据库；MinIO/Artifact 保存、管理员恢复及确认后精确清理仍待实现。

### 工作目录归属与生命周期

- 由平台依据已认证的 user、Run、Task 分配任务工作目录和 `workspace_reference`，模型只使用获准的相对路径；无 Project 的任务也可以创建临时目录，不以项目分类页面为前置。项目 Workspace 与任务临时目录不能共用一个可写根目录。
- 输入文件从当前任务获准的不可变 UserFile/Artifact 物化，核对哈希后放在只读输入区；工作区和输出区单独可写。API/受信服务负责对象存储读写，执行容器不获得 MinIO 或 Provider 密钥。
- 同一任务后续工具调用复用该工作目录，不要求复用 Python 进程内变量；首版 Python 为每次调用独立进程，不实现 Notebook 内核。可每次创建临时容器、仅挂载该任务目录，实现文件连续性；模型无权指定宿主路径、容器或挂载参数。
- 写入与执行在同一 Workspace 串行，读取与写入互斥或返回明确冲突。取消/终止时先停止实际进程，确认没有执行后保存获准输出 Artifact；校验文件类型、路径、大小及归属，拒绝通过软/硬链接和特殊文件导出其他数据。
- 输出持久化成功后才按任务策略清理精确工作目录；保存失败保留待处理记录，不因清理删除唯一结果。未知执行结果不自动重跑。API/执行器崩溃后的工作目录发现与处理必须记录状态，阶段10完成前不宣称自动续跑。

### 复用工具定义与调用过程

`RegisteredTool.input_schema → Provider ToolDefinition → ToolCall → ToolExecutionRequest → Registry/权限/Workspace 检查 → ExecutionBackend → ToolExecutionResult → Tool Message` 是唯一模型工具调用流程。

- `ToolDefinition`、`ToolCall` 和 Tool Message 已在 `packages/models` 定义；内置只读 Registry、执行服务和审计写入已有实现。任务工作目录及 Python/Shell 还需补执行权限、环境和结果保存，不能仅登记 Schema 就声称工具可用。
- 文件工具复用既定 `list_run_files`、`get_file_outline`、`search_file_content`、`read_file_content`、`read_file_table`；工作目录工具复用 `list_files`、`read_file`、`write_file` 等既有目录。第一批文件分析不依赖 Git 工具，也不新增一个强制“文件 Agent”。
- Python／Shell 使用已有 `run_command` 的结构化 `executable`、`arguments[]`、相对工作目录和有界 stdin，不再新增一套通用 `execute_python`/`execute_shell` 合同。平台把允许的解释器标识解析为镜像内固定程序，宿主启动器始终使用参数数组和 `shell=False`。
- Python 只在任务沙箱内执行，首版允许已保存的获准脚本路径或有界 stdin，使用隔离启动参数；脚本读写仍依赖容器挂载/权限约束。不能把“可执行文件在允许列表”当成脚本行为已获安全证明。
- Shell 作为显式 `execute` 策略下的解释器运行，只接受工作目录内受控脚本或有界 stdin；首版不允许模型通过 `sh -c`、`bash -c` 拼出另一套未审计命令入口。脚本中的管道/子进程由容器内 Shell 解释，不能在宿主运行；其权限等同通用代码执行，不能按只读工具授权。
- 工具由 Task 明确授予能力，部署策略控制是否启用，模型不能自报 owner、权限、超时上限或 Workspace。审核节点的自然语言同意不能代替程序授权。未授权时不向模型提供定义，绕过调用时仍在执行前拒绝。
- Agent 模块将工具结果和来源放回模型消息，控制循环、费用和取消；执行 Service 本身不调用模型。两部分在本计划共同验收；保留 `model_only_v1` 无工具行为，通过 `tool_enabled_v1` 启用。

### pip 与依赖规则

- pip 仅在受信镜像构建时使用。依赖新增通过修改清单、构建、测试、固定新镜像版本和发布完成；任务期间不提供安装工具或软件源访问，不写宿主/基础镜像的 Python 环境。
- 不把 `PIP_NO_INDEX` 或命令字符串过滤当成隔离。运行镜像与依赖只读、容器网络禁用；可在后续镜像实现中不携带构建用 pip，Python 任意代码仍按执行权限处理。任务目录能写文件不等于授予包安装或联网权限，也不承诺静态检查能识别所有自带 Python 代码。
- 缺少依赖时明确返回环境能力不足，不能隐式联网安装、切到宿主运行或让模型改用 Docker。首次镜像下载/构建耗时与任务执行耗时分开记录。

### 前置测试与交付限制

先补 Registry/参数/授权/重复 Tool Call 测试，再实现工作目录物化和执行。真实容器测试至少覆盖双用户双任务隔离、第二次调用读取第一次输出、输入只读、链接逃逸、环境变量/密钥不可见、网络/安装请求拒绝、stdout/stderr 并发输出、非零退出、超时和取消、结果存储失败及精确清理。Python/Shell 均按可执行任意代码的风险验证，不能仅凭固定解析器安全测试通过就开放。

只读文件工具已可本地使用；`run_command` 的本地执行器已实施，但在接入数据库身份、调用记录、Artifact 与取消流程之前仍不向 Agent 启用。没有实施任务目录表迁移。下一步按此处现有工具定义和调用过程完成受信执行服务连接及 Agent 接入，不把管理员 CLI 变成模型直连入口。阶段10负责脱离观察连接的执行所有权与重启恢复，本工作项不另建内存后台任务冒充可靠 Worker。

## 核心合同

阶段2统一解析实施补充：历史 Poppler 隔离启动组件已有 macOS 验证，2026-10-04 目标 Linux API 容器的嵌套隔离失败。2026-10-07 已在本地代码中迁移到专用解析执行器；该迁移仍不代表通用工具登记、授权器或模型工具已完成，固定格式解析接口不能接受任意命令。

### 工具描述

工具注册表中的执行描述建议命名为 `RegisteredTool`，避免与 Provider 合同中的 `ToolDefinition` 混为一谈：

```python
class RegisteredTool:
    name: str
    version: str
    description: str
    input_schema: dict
    output_schema: dict
    usage_examples: list[dict]
    implementation_reference: str
    execution_environment_reference: str | None
    dependency_versions: dict[str, str]
    visibility_scope: str
    required_capabilities: set[ToolCapability]
    is_read_only: bool
    is_concurrency_safe: bool
    default_timeout_seconds: int
    maximum_timeout_seconds: int
```

- 内置工具的 Schema 从 Pydantic 输入/输出类型生成；生成工具使用经校验的声明式 Schema。Registry 保存统一 Schema，Provider `ToolDefinition` 直接从它投影，不手工维护第二份输入合同，也不在 API 中导入生成代码。
- Registry 拒绝重复 `(name, version)`、不符合命名规则的工具和没有输入/输出模型的执行器。
- 模型请求只看到本次任务被策略允许的工具子集，不把“注册成功”解释为“任何 Agent 都有权调用”。
- 工具版本进入审计记录；版本变化不能改变已经开始的 Tool Call 语义。

### 执行请求

建议内部请求命名为 `ToolExecutionRequest`：

```text
platform_tool_call_id
provider_tool_call_id
model_attempt_id
run_id
task_id
user_id
project_id
tool_name
tool_version
arguments
workspace_reference
idempotency_key
requested_timeout_seconds
```

这些 ID 由内部调用上下文和数据库关系确认。模型只能产生 `provider_tool_call_id`、工具名和 arguments，不能自行声明 `user_id`、Workspace、权限、超时上限或幂等键。

### 执行结果

建议返回 `ToolExecutionResult`：

```text
platform_tool_call_id
status
output
output_preview
result_artifact_id
stdout_preview
stderr_preview
exit_code
duration_ms
is_output_truncated
error_code
error_message
```

- `output` 必须符合工具输出模型，并具有总字节上限。
- 大输出保存为 Artifact，模型只接收有界摘要和 `artifact_id`，不接收 MinIO URI。
- stdout、stderr 和异常文本先脱敏再保存；凭据、Authorization、Cookie 和环境变量值不进入模型上下文。
- Tool Runtime 返回事实，不生成自然语言解释；如何向模型表达由阶段3统一处理。

## 工具目录和实施顺序

阶段7仍是一个阶段，不拆成新的阶段编号。按风险从低到高逐项启用：

| 工具 | 含义 | 初始能力 | 并发规则 | 主要限制 |
|---|---|---|---|---|
| `list_files` | 列出 Workspace 内目录与文件元数据 | `read` | 没有写工具运行时可并行 | 不跟随符号链接；限制深度、数量和隐藏目录 |
| `read_file` | 读取 Workspace 内文本文件的有界片段 | `read` | 没有同文件写入时可并行 | 拒绝二进制、超大文件和越界路径；支持行范围而非整库读取 |
| `search_text` | 使用 ripgrep 搜索文本并返回文件、行号和证据 | `read` | 可并行，但受每 Run 并发上限约束 | 固定参数模板、`--no-config`、不跟随链接、限制结果数/单行长度/总输出 |
| `git_status` | 返回隔离 Workspace 的稳定 Git 状态 | `read` | 与写工具互斥 | 使用 Porcelain v2；不执行 hook，不修改配置或索引 |
| `git_diff` | 返回受限差异及统计 | `read` | 与写工具互斥 | 禁止外部 diff 驱动；限制路径、大小和二进制内容 |
| `write_file` | 在可写隔离 Workspace 创建或完整替换单个文本文件 | `write` | 同一 Workspace 写操作串行 | 原子临时文件替换；禁止覆盖符号链接、超大文件和仓库外路径 |
| `apply_patch` | 应用可复核的文本补丁 | `write` | 同一 Workspace 写操作串行 | 先解析和预检全部目标，避免可预见的部分写入；意外中断时返回实际修改文件清单，不虚构全部回滚 |
| `run_command` | 在隔离执行后端运行结构化 argv | `execute` | 默认串行 | 不使用 Shell 字符串；命令允许列表；无网络；限制进程、CPU、内存、时间和输出 |

通用工具的原定实施批次先完成 `list_files`、`read_file`、`search_text`、`git_status` 和 `git_diff`，再在路径竞争测试通过后增加 `write_file`、`apply_patch`。2026 年 10 月 6 日确认的文件解析部署与任务文件分析优先按上方专项计划执行，不以 Git 工具实现为前置条件，也不恢复其他暂停项。`run_command` 必须等隔离执行后端通过真实 Docker 安全验证后才能启用；普通进程单元测试通过不代表该工具可用。

## 权限模型

### 能力类别

沿用总体规划中的五类能力：

```text
read
write
execute
network
external_side_effect
```

它们不是简单从低到高的单一枚举。例如命令可能同时需要 `execute + network`。现有 `risk_level` 继续保存便于查询的最高风险摘要，同时增加结构化 `required_capabilities` 和策略证据，不能只用一个字符串完成授权。

### 判定输入

权限判定器至少读取：

```text
tool name + version
registered capabilities
run/task/user/project relationship
workspace reference and access mode
task-granted capabilities
deployment policy version
requested paths/command/network
whether an isolated backend is available
```

模型输入中的 `risk_level`、`allowed_paths`、`requires_approval` 或类似字段一律不可信。

### 已注册且已启用工具的默认规则

下表不启用尚未实现或暂停的工具；Git/联网等仍按文首范围保持关闭。

| 操作 | 默认决定 |
|---|---|
| 读取绑定 Workspace 内普通项目文件 | 策略允许 |
| 搜索代码 | 策略允许 |
| Git status/diff | 策略允许 |
| 写入显式可写的隔离 Workspace | Task 已授予 `write` 时允许 |
| 在原始仓库写入 | 拒绝 |
| 执行命令 | 只有隔离后端、允许命令和 `execute` 能力同时满足时允许 |
| 网络访问 | 拒绝 |
| 外部副作用 | 拒绝 |
| 读取密钥、系统目录或 Workspace 外路径 | 拒绝 |
| 需要用户批准的操作 | 记录 `approval_required` 后等待；批准产品接口未实现前安全停止，不伪造批准 |

最终用户批准复用阶段5当前用户身份，相关交互和服务端一次性批准在本计划统一交付；不等待阶段4全部完成。在批准能力完成前，策略要求批准的调用只能停止，不能由内部 API Key 自动代替用户同意。

## Workspace 与路径安全

- Tool Runtime 只接受平台创建并登记的 `workspace_reference`，不接受模型提交绝对路径。
- 执行上下文把 reference 解析为规范 Workspace root；工具输入路径必须是相对路径。
- 读取前解析规范路径并确认仍在 root 内；不跟随符号链接。写入不存在文件时还要解析和验证最近存在父目录。
- `.ssh`、`.aws`、`.gnupg`、凭据文件、系统目录、宿主用户目录和 Docker Socket 永久拒绝，即使它们被软链接进 Workspace。
- 文件类型判断不能只依赖扩展名；读取工具拒绝包含 NUL 字节的内容，并使用严格字节上限。
- 路径预检与实际打开之间存在竞争窗口。真实安全门禁必须包含符号链接替换测试；高风险写入优先在独占隔离 Workspace 内完成，不能只依赖字符串 `startswith`。
- Git 工具内部可以访问仓库元数据，但模型不能通过 `read_file` 直接遍历 `.git`。

## 命令执行与容器隔离

`run_command` 接收结构化内容：

```text
executable
arguments[]
working_directory
timeout_seconds
stdin_text（可选且有界）
```

约束：

- 宿主执行器使用参数数组执行，不拼接 Shell 命令，不使用 `shell=True`。后续受控 Shell 解释器仅按上方任务工具计划在容器内运行脚本或 stdin，不把脚本文本传给宿主 Shell。
- 可执行文件必须来自按任务类型配置的允许列表；不继承宿主完整 `PATH` 或环境变量。
- 子进程使用最小环境变量白名单，不传入平台 API Key、数据库、MinIO 或 Provider 凭据。
- 超时先终止整个进程组，宽限期后强制结束；必须同时持续读取 stdout/stderr，避免管道填满造成死锁。
- 输出按流和总量限制；超过预览上限继续有界排空或终止，并标记截断，不能无限读入内存。
- 非零退出码是已完成的命令结果，不等同于 Tool Runtime 内部异常。

生产执行后端至少满足：非 root 用户、只挂载指定 Workspace、根文件系统只读、禁止 privileged/host PID/host network、删除额外 Linux capabilities、`no-new-privileges`、默认无网络、进程/CPU/内存限制、受控临时目录、确定超时和容器清理。Docker 官方说明容器默认没有 CPU/内存限制，因此这些限制必须显式配置。

Docker daemon 或 socket 本身具有高权限。API 进程不能把 socket 暴露给模型生成的命令；实施时优先将隔离执行适配器放在权限更小的独立执行边界。若只能让 API 进程直接访问 Docker daemon，必须在风险评审后才能启用 `run_command`，阶段7状态继续保持“进行中”。

## 同步执行和事务边界

```text
阶段3或内部测试提交 ToolExecutionRequest
  ↓
Registry 查找固定版本 + Pydantic 参数校验
  ↓
关系与 Workspace 校验
  ↓
PermissionPolicy 计算并保存决定
  ↓ commit：先留下 requested/denied 事实
ExecutionBackend 执行（不持有数据库事务）
  ↓
结果校验、脱敏、截断和 Artifact 保存
  ↓ commit
更新 llm_tool_calls 为 completed/failed/timed_out/outcome_unknown
  ↓
返回 ToolExecutionResult
```

- 权限事实无法提交时不执行工具，避免无审计副作用。
- 工具执行期间不持有请求数据库事务或连接。
- 只读工具在结果保存失败后可以使用相同幂等键安全重建；写入和执行工具不能盲目重试。
- 写入或命令已经产生副作用，但结果保存失败时标记 `outcome_unknown`，交给阶段3决定重新调查或请求用户确认。
- 同一 `(model_attempt_id, provider_tool_call_id)` 只能创建一个逻辑 Tool Call；重复收到时返回已有终态，运行中或未知状态不重复执行。
- 当前同步模式下请求取消会传播到执行后端，但只能在安全点终止；已经完成的文件写入或命令副作用不会自动回滚。

## 状态与错误合同

建议 Tool Call 状态固定为：

```text
requested
permission_denied
approval_required
running
completed
failed
timed_out
cancelled
outcome_unknown
```

稳定错误至少区分：

```text
tool_not_registered
tool_version_not_available
invalid_tool_arguments
tool_permission_denied
tool_approval_required
workspace_not_found
workspace_path_denied
workspace_changed
tool_dependency_unavailable
tool_execution_timeout
tool_output_limit_exceeded
tool_process_failed
tool_result_persistence_failed
tool_execution_outcome_unknown
```

- 输入、权限和路径错误不可重试。

- timeout 不等于进程一定没有产生副作用；写/执行工具超时后根据执行后端确认结果决定 `timed_out` 或 `outcome_unknown`。
- 对外错误不包含宿主绝对路径、命令环境、容器 ID、密钥或完整 stderr；内部审计保存脱敏和有界证据。

- 工具实际执行通过内部 Python Service 调用。若未来 Worker 跨进程部署需要 RPC，再根据真实部署边界单独规划认证、超时和幂等，不在阶段7预建空接口。

## 初始资源上限建议

以下是编码时的测试基线，不是不可调整的产品承诺；全部进入带单位的配置并设置硬上限：

| 资源 | 建议初值 | 硬边界目的 |
|---|---:|---|
| 单次目录返回 | 500 项 | 防止超大目录耗尽上下文 |
| 目录递归深度 | 8 层 | 防止无界遍历 |
| 单次文件读取 | 1 MiB | 防止读取大型或生成文件 |
| 单次写入文本 | 1 MiB | 防止模型写入异常大文件 |
| 搜索匹配 | 500 条 | 保持证据可消费 |
| 搜索预览（后续目标） | 256 KiB | 尚未启用的搜索工具建议值，不适用于命令执行器 |
| 当前命令输出 | stdout、stderr 各 32 KiB | 与本地执行器一致，分别返回截断标记 |
| 搜索超时 | 30 秒 | 限制代码库扫描时间 |
| 当前命令默认超时 | 30 秒 | 与本地执行器一致 |
| 当前命令最大超时 | 60 秒 | 受信调用方也不能突破此上限；扩大限制须另行验证 |
| 每 Run 并发只读工具 | 4 | 避免文件句柄和 CPU 突发 |
| 每 Workspace 并发写工具 | 1 | 防止文件竞争和补丁交错 |

超过预览但未超过 Artifact 上限时可以保存完整结果 Artifact；超过执行后端硬输出上限时终止或丢弃后续输出并返回明确截断事实，不能静默返回看似完整的内容。

## 测试设计

权限、安全、状态、幂等和公共合同必须测试先行。

### 合同和 Registry

- 重复名称/版本、未知工具、未知版本、额外字段、非法参数、过大输入和输出 Schema 不匹配。
- Provider `ToolDefinition` 与 Pydantic 输入模型保持一致，不存在第二份漂移 Schema。
- 未授权工具不会出现在提供给模型的工具列表中。

### 路径和文件

- 正常相对路径、`..` 越界、绝对路径、符号链接到外部、父目录符号链接替换、隐藏凭据目录、NUL 二进制和超大文件。
- 写入成功、目标已变化、临时文件失败、原子替换失败、磁盘满和取消。
- 两个并发写请求不能交错；读写竞争返回稳定冲突或串行结果。

### 搜索和 Git

- 搜索正常、零匹配、非法表达式、结果上限、超长行、超时、`rg` 缺失和含连字符查询。
- 明确传入 `--no-config`，用户级 ripgrep 配置不能扩大搜索范围。
- Git status Porcelain v2 解析文件名边界；Git diff 禁止外部驱动、二进制大输出和仓库外路径。

### 命令和隔离

- 允许 argv、未允许 executable、Shell 元字符作为普通参数、工作目录越界、环境变量过滤、网络拒绝和容器无权读取宿主目录。
- stdout/stderr 同时大量输出不会死锁；超时终止整个进程组；取消、非零退出、信号退出和容器清理均留下事实。
- Docker CPU、内存和进程限制通过真实基础设施测试确认；只检查启动参数不算隔离验证。

### 审计和恢复

- 权限事实提交失败时工具不执行；重复 provider Tool Call 不重复执行。
- 完成后数据库写入失败：只读工具可重建，写/执行工具进入 `outcome_unknown`。
- Artifact 上传成功但数据库绑定失败会留下可识别孤儿对象，并有受控清理或补偿测试。
- 输入、输出、日志、错误和审计查询均不泄露 API Key、Provider 凭据、Cookie、绝对宿主路径和环境值。

## 实施步骤

以文首统一工作项为交付顺序：先连续使用基础工具，再发现、代码组合、生成/复用工具。固定 PDF/Office 的本地验证已有记录，服务器验收暂停，不再作为当前工具开发前置。下表仅为执行组件的编码检查清单，需与同一工作项中的模型循环和 Web 验收一起完成，不能独立替代业务交付。

| 步骤 | 修改对象 | 预期结果 | 验证方式 |
|---|---|---|---|
| 1 | 合同、状态、Registry 和权限测试 | 固定工具语义、授权输入和稳定错误 | 参数化单元测试、模型合同兼容测试 |
| 2 | `packages/tools` 最小骨架 | 可注册和执行纯测试工具，不依赖 FastAPI/数据库 | 包测试、架构依赖测试、Ruff |
| 3 | Workspace/path policy | 所有工具共享唯一规范路径边界 | 临时目录、符号链接和竞争测试 |
| 4 | 只读文件和搜索工具；Git 后置 | 返回有界、结构化、可复核证据 | 文件集成、ripgrep 真实进程测试；启用 Git 时另验收 |
| 5 | Tool Call 迁移和 API 持久化适配 | 权限前事实、终态、幂等和 Artifact 可查询 | MySQL 迁移、事务和内部审计测试 |
| 6 | 写文件和补丁 | 只修改隔离可写 Workspace，失败不留下部分补丁 | 原子写、并发、补丁预检和 Git diff 测试 |
| 7 | 隔离执行后端与 `run_command` | 结构化 argv 在无网络、受限资源环境中执行 | Docker 基础设施、安全逃逸和资源测试 |
| 8 | Agent 循环、消息续接与 Web 装配 | 模型连续调用、失败后修正、最终结果有依据；同步限制公开 | Provider 协议、ASGI/Service、浏览器与进程清理测试 |
| 9 | 文档与阶段验收 | 限制、未支持能力和运行方式与代码一致 | 完整快速测试、MySQL、MinIO、Docker 验证 |

## 失败与恢复设计

- 读取工具失败不写业务结果；保留已提交的失败 Tool Call 事实。
- 写入工具采用单 Workspace 互斥和原子文件替换；多文件补丁在预检全部目标后执行，执行中异常必须报告已修改文件，不能声称全部回滚。
- 命令调用不自动重试。只有错误发生在进程启动前且确定没有执行时，调用方才可使用同一逻辑 Tool Call 重新尝试。
- 初期明确的同步验证模式中，请求断开会取消在途工具，不能宣称后台继续；若无法确认副作用则记录 `outcome_unknown`。后台工作项完成后由 Worker 持有执行权，观察连接断开不取消，仅显式取消请求可停止。
- 后台恢复实施前，API 重启不会自动续跑 Tool Call；遗留记录需结合实际执行者状态核对，不把所有运行中记录直接改为失败。接入 Worker 后按租约与执行尝试确认，避免 API 重启误伤其他执行者。

## 风险与停止条件

- 没有隔离执行后端时，可以完成只读与受控文件工具，但不能启用 `run_command`，阶段7不能标记“已完成”。
- 无法可靠约束 Workspace root 或符号链接时，停止文件写入和命令执行，只保留安全的合同/Registry 工作。
- 需要网络或外部副作用时，停止并单独确定域名、凭据、幂等和用户批准；阶段7默认拒绝。
- 要求从普通用户 HTTP 请求直接执行命令时，停止并先完成阶段5身份、授权、限流以及部署隔离评审。
- Docker 只能以 privileged、host network、host PID 或挂载 Docker Socket 到执行容器的方式运行时，拒绝启用命令工具。

## 完成标准

- 工具注册、输入/输出 Schema、权限和错误合同稳定，未知工具或非法输入不会进入执行器。
- 本次启用的文件/搜索/写入/补丁/命令工具分别通过安全和失败测试；Git 属于后续暂停项，不是首批交付条件。
- 读取、写入和执行都不能越过绑定 Workspace；原始仓库写入、网络和外部副作用默认拒绝。
- 写入和命令执行只在通过真实验证的隔离环境运行；超时、资源和输出均有硬上限。
- 每次允许、拒绝、失败、超时、取消和未知结果都形成可查询、脱敏的 `llm_tool_calls` 事实。
- 重复 Tool Call 不重复产生副作用；无法确认结果时不会自动重试或伪造失败/成功。
- 执行服务可脱离 Agent 独立测试，但主计划验收必须包含模型持续调用、发现、代码组合和生成工具，不能只验收 Registry/Service 即宣布完整能力完成。
- 按文首工作项分别记录完成；长期复用、后台任务和外部工具未验收时继续列为未开始或进行中。Git 暂停不阻塞已独立验收的只读/计算工具，但不得据此宣称 Git 可用。

## 官方依据

- [Python asyncio subprocess](https://docs.python.org/3/library/asyncio-subprocess.html)：确认参数化异步进程接口、超时需要由 `asyncio.wait_for()` 控制，以及管道输出必须持续读取以避免死锁。
- [Python subprocess security considerations](https://docs.python.org/3/library/subprocess.html#security-considerations)：确认 Shell 调用的转义责任；本阶段因此默认使用参数数组和 `shell=False`。
- [Docker Engine security](https://docs.docker.com/engine/security/)：确认 daemon 权限边界、非特权用户、Linux capabilities 和容器隔离风险。
- [Docker resource constraints](https://docs.docker.com/engine/containers/resource_constraints/)：确认容器默认没有 CPU/内存限制，阶段7必须显式设置资源上限。
- [Docker user namespace isolation](https://docs.docker.com/engine/security/userns-remap/)：确认非特权用户和 user namespace 的隔离作用及 daemon 仍可能具有高权限的边界。
- [ripgrep User Guide](https://github.com/BurntSushi/ripgrep/blob/master/GUIDE.md)：确认默认忽略、符号链接和 `--no-config` 等搜索行为。
- [Git status Porcelain v2](https://git-scm.com/docs/git-status.html#_porcelain_format_version_2)：确认供程序解析的稳定状态格式。
- [Git diff](https://git-scm.com/docs/git-diff)：确认差异命令能力；阶段7只开放固定参数子集并禁用外部 diff 驱动。
